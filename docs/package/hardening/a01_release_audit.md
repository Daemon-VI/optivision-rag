## 3. Checked and correct
- Metadata: name `optivision-rag`; version dynamic from `optivision.__version__` (single literal); `requires-python >=3.10`; classifiers 3.10-3.13 + Beta; license MIT with `license-files`; URLs point to Daemon-VI/optivision-rag; extras vlm/corpus/bench/app/merge/dev; dependencies unchanged vs 0.3.0. Metadata-Version 2.4. `twine check --strict` passes on both artifacts.
- Wheel: 108 files, `optivision/` plus dist-info only; core (36 files), backends, adapters, ext, legacy, testing, stages and presets/*.yaml (the only non-.py package data; it ships). No tests, fixtures, research data, reports or scripts shipped. All 97 modules import from the installed wheel.
- Version consistency: `__init__` 0.3.0 = npm/package.json 0.3.0 = wheel METADATA; `tests/test_release_versions.py` passes. vscode-extension is versioned independently (0.1.0) per RELEASING.md.
- PACKAGE.md has no relative links (good for PyPI). Relative links in README, PACKAGE, CHANGELOG, npm README and RELEASING all resolve in the repo (script found none broken).
- Research wording in PACKAGE.md respects the brief (H5 failed, XH not run, agreement is not quality, no guarantee).
- CI: `ci.yml` on every push and PR; ubuntu, Python 3.10 and 3.13; `pip install -e ".[dev,corpus]"` (dev includes scipy); `pytest -q`; on 3.13 only `ruff check src tests` and `python -m build`; a node job on ubuntu and windows builds the wheel and runs the npm launcher smoke test against it. LFS is not fetched by checkout (consistent with tests that skip on pointer files). Publish: only on a published GitHub release; build job checks tag vs `__version__` and npm version, runs tests, builds; then `pypi` (environment `pypi`, OIDC), then `npm` (OIDC, provenance). Nothing publishes on a plain tag push.
- certify without SciPy fails with a clear actionable ImportError, never a silent reduced list. `optivision certify` on a missing file exits 2 with a readable message.

## 4. Steps for a 0.4.0 release, in order
1. Owner decisions: version number and merge strategy (package-universal into main).
2. `src/optivision/__init__.py:54` `__version__ = "0.4.0"` and `npm/package.json` `"version": "0.4.0"` (identical; publish.yml greps the literal `__version__ = "X"` line).
3. Update `tests/test_api_compat.py:302` (rename `test_version_is_still_0_3_0_and_a_literal`) and `tests/test_core_certificate.py:216`.
4. `CHANGELOG.md`: merge the two "Unreleased" sections into `## 0.4.0 (date)`; remove branch and "nothing is released" wording.
5. `PACKAGE.md` and `README.md`: remove unreleased/branch/clone wording (A01-01/02); absolute GitHub URLs for docs in PACKAGE.md; fix README tree comments (lines 535, 545).
6. Optional: descriptions (A01-07); npm/README.md certify note (A01-04); header note on docs that say "`__version__` stays 0.3.0" (API_DESIGN.md:3, MIGRATION.md:3, UNIVERSAL_PACKAGE_DESIGN D18, guide/README, BUILD_AND_PORTABILITY_REPORT, TEST_REPORT).
7. Run locally: full pytest, `ruff check src tests`, `python -m build`, `twine check --strict dist/*`, npm smoke test against the wheel (RELEASING.md step 2).
8. Merge to `main`, push, wait for green CI (both Python cells, both node OSes).
9. Confirm the PyPI trusted publisher (Daemon-VI/optivision-rag, publish.yml, environment pypi), the GitHub environment `pypi`, and the npm trusted publisher exist (not verifiable here).
10. Draft a GitHub release with new tag `v0.4.0` on the merge commit and publish it: build -> pypi -> npm.
11. Verify from a clean env: `pipx install optivision-rag`, `optivision --version` prints 0.4.0, `npx optivision-rag@0.4.0 --version`, and a `certify` smoke with `[merge]`.
